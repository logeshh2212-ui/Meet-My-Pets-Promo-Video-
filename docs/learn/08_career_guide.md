## 8.2 The pitches

**30 seconds (elevator):**
> "I built a 30-second launch film for a pet social app, entirely in code. It's a deterministic rendering engine in TypeScript and three.js: every frame is a function of time, so a headless browser can render it frame by frame into ffmpeg. The app's real Figma screens are cut into 3D widgets that a paw 'taps', and everything is locked to a beat grid I measured from the music. The interesting part was engineering: I found a 6× speed-up from a wrong GPU backend flag and fixed GPU memory crashes by restructuring the render."

**2 minutes (interview "tell me about a project"):**
1. **Context:** a startup needed a launch video; I had a music-video engine (P(doom)) that synced visuals to lyrics using AI audio models.
2. **Goal:** a 30 s, YouTube 16:9 film where every feature is shown interactively, on the beat.
3. **What I built:** a widget kit (Figma crops → 3D objects with state), shot templates with camera keyframes, per-act 3D worlds, a measured beat grid, synthesised sound effects, and a render pipeline.
4. **Hard problems:** the beat detector said 97 BPM and was wrong; I cross-checked with bass gaps and found the true bar of 3.311 s. Rendering was 1 s/frame because a Mac-only flag forced CPU rendering on Windows; fixing it gave 6×. GPU crashes → shared buffers and per-shot rendering.
5. **Result:** a 1835-frame 60 fps film, and a clear roadmap to turn it into an AI video generator (LLM writes a validated storyboard JSON; the engine renders it).

## 8.3 STAR stories (Situation, Task, Action, Result)

**STAR** is the standard way to answer "tell me about a time when…".

**1. Debugging a performance problem**
- *S:* rendering took about 1 second per frame; a 30 s film would take hours.
- *T:* find out why and make it fast enough to iterate.
- *A:* I didn't guess. I wrote a tiny script that printed which GPU Chrome actually used. It said SwiftShader (CPU). The render script forced a macOS-only graphics flag; I made the flag OS-specific.
- *R:* 130–220 ms per frame, about 6× faster. Lesson: measure first.

**2. A confident but wrong algorithm**
- *S:* automatic tempo detection said 97 BPM.
- *T:* get a beat grid I could trust for every cut.
- *A:* I noticed edits didn't feel on the music, so I looked at an independent signal: the bass drops out before every bar. The gaps were perfectly regular: 3.311 s.
- *R:* every cut lands on a downbeat. Lesson: cross-check model outputs with an independent signal. Directly relevant to AI work (evaluation, hallucination checks).

**3. Working with limited hardware**
- *S:* renders crashed with "Target crashed" on an integrated GPU.
- *T:* make the full film render reliably.
- *A:* found the cause (GPU memory: nine scenes with large textures, shadow maps and MSAA buffers in each browser page), shared one multisampled buffer, shrank shadow maps, rendered per shot and joined with ffmpeg.
- *R:* reliable renders; failures became local and cheap to retry.

**4. Handling changing requirements**
- *S:* the format changed from 76 s vertical to 16:9 to 30 s; the style changed from "phone on screen" to "interactive widgets in 3D worlds".
- *T:* deliver without restarting each time.
- *A:* kept one source of truth (the storyboard JSON, generated by a script from the beat grid) and reusable kits, so changes were data edits, not rewrites.
- *R:* each direction change took hours, not days.

## 8.4 Interview questions with answers

**Q: What does "deterministic rendering" mean and why does it matter?**
A: The frame at time `t` depends only on `t` (and fixed data), not on how fast the computer is or what came before. So preview and export match exactly, any frame can be rendered alone, and frames can be split across workers.

**Q: Why render in a browser instead of a video tool?**
A: The browser gives a mature GPU API (WebGL), text rendering, fonts and a live preview for free. Playwright makes it scriptable. The trade-off is overhead in moving pixels out (we use a WebSocket to ffmpeg).

**Q: How does motion blur work here?**
A: For each output frame we render several sub-frames inside the "shutter" time and average them. Adaptive mode only adds samples to 32-pixel tiles that actually move, to save time.

**Q: How would you add AI to this?**
A: An LLM planner that outputs a storyboard JSON, validated against a schema, with a catalogue of templates; a vision model to parse screens into widgets; a beat tracker for any music; a vision model for automatic QA on contact sheets. The renderer stays deterministic so the product UI is pixel-exact.

**Q: What is CTC forced alignment?**
A: An acoustic model outputs letter probabilities every ~20 ms. Because we already know the lyrics, we search for the best time path of those known letters through the probabilities (dynamic programming). It gives word timings more reliably than free recognition.

**Q: How do you know your AI output is correct?**
A: Use an independent check: a second method (Whisper vs CTC), a different signal (bass gaps vs onset tempo), schema validation, and a small labelled test set. Measure, don't trust.

**Q: What would you do differently?**
A: Make templates data-driven from the start; write automated visual tests (render stills and compare to references); check the GPU backend on day one.

**Q: How did you handle the GPU memory issue?**
A: Profiled the cause (textures, shadow maps, MSAA targets per scene × 2 pages), shared resources, reduced sizes, and changed the job structure (per-shot renders). Also added retries for a rare startup failure.

## 8.8 Portfolio and job-search tips

- **Show the video first**, then the architecture diagram, then one hard problem you solved.
- Write a **README** with: what it does, a GIF, how to run it, an architecture diagram, results with numbers (6× faster, 1835 frames).
- Write **one blog post per war story**. Short, specific posts get read.
- On your CV, use numbers: *"Cut render time 6× by diagnosing a GPU backend fallback."*
- Keep learning in public: GitHub commits, short posts, small demos.
